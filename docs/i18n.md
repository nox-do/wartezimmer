# i18n — Übersetzungsrichtlinie

## Kurzfassung

| Oberfläche                 | Sprachen                                          | Mechanismus                                          |
| -------------------------- | ------------------------------------------------- | ---------------------------------------------------- |
| **Terminal** (`/terminal`) | de-DE, en-GB, tr-TR, ru-RU, uk-UA (Ops-gesteuert) | `t()` / `tf()` + Sprachwahl am Terminal              |
| **Portal** (`/portal`)     | wie Terminal (gleiche Ops-Liste)                  | gleiche Patienten-Locale wie Terminal (localStorage) |
| **MFA, Ops, TV**           | **nur de-DE**                                     | `de-DE.ts`; Locale erzwingt `STAFF_LOCALE`           |

Die i18n-Infrastruktur (`I18nManager`, Locale-Dateien, `t`/`tf`) bleibt für spätere Erweiterungen erhalten. Neue Staff-Texte gehören in `de-DE.ts`, nicht in `en-GB.ts` / `tr-TR.ts` / `ru-RU.ts` / `uk-UA.ts`.

## Kanonische Locale-Liste

**Single source of truth:** `packages/domain/src/terminal-patient-locales.ts`

- `TERMINAL_PATIENT_LOCALES` — alle unterstützten Patienten-Codes
- `TerminalPatientLocale` — Typ für Backend, OpenAPI und UI (`AppLocale` ist ein Alias)
- `normalizeTerminalPatientLocales` — Ops-Patch / DB; `de-DE` ist immer enthalten

UI leitet `APP_LOCALES`, `PATIENT_LANGUAGE_OPTIONS` und Tastatur-Layouts daraus ab — keine parallele Liste pflegen.

## Locale-Auswahl

`getAppInitialLocale()` in `ui/src/lib/i18n/patient-locale.ts`:

- **Patientenpfade** (`/terminal`, `/portal`): gespeicherte Terminal-Sprache oder Browser-Fallback (`getBrowserLocale`)
- **Alle anderen Pfade**: immer `de-DE` (`STAFF_LOCALE`), unabhängig von der Browser-Sprache

Beim Wechsel Terminal → MFA wechselt das Root-Layout die Locale zurück auf Deutsch.

### Ops: aktivierte Sprachen

Praxis schaltet Sprachen unter MFA → Betrieb (`terminalPatientLocales`). Terminal liest die Liste aus dem Heartbeat; Portal aus `GET /api/v1/ops/patient-locales`. `PatientLangPicker` filtert die Buttons und setzt bei Deaktivierung auf `de-DE` zurück.

## Locale-Dateien

- **`de-DE.ts`** — vollständiges Wörterbuch (Staff + Patient); **`AppDict`** leitet sich daraus ab (`core/AppDict.ts`)
- **`en-GB.ts` / `tr-TR.ts` / `ru-RU.ts` / `uk-UA.ts`** — `...deDict` + Overrides nur für `terminal`, `portal` und minimale `ui`-Strings (Laden/Toast auf Patientenpfaden)

Keine partiellen Ops-/MFA-/Auth-Übersetzungen in Patienten-Locales — das erzeugte den Eindruck eines mehrsprachigen Ops-Setups, obwohl Staff-UI Deutsch ist.

## API (`t` / `tf`)

- **`TranslationKey`** (`ui/src/lib/i18n/core/translation-keys.ts`) — Dot-Notation aus `AppDict`, z. B. `terminal.langDe`
- **`t(key)`** / **`tf(key, vars)`** — typisiert für Literale; dynamische Keys (Template-Strings) bleiben als `string` möglich
- Platzhalter: `{name}` in Strings, Ersetzung via `tf('mfa.settings.dayHintLead', { greeting })`

Bootstrap: Root-`+layout.svelte` ruft `initI18n(getAppInitialLocale(pathname))` auf.

## Ops Setup-Hints

Server-Codes aus dem Setup-Assistenten werden in `ui/src/lib/ops/setup-check-hints.ts` als **deutsche Konstanten** gemappt — nicht über `t('ops.setup.checkHint.*')`. IT-Setup ist bewusst deutsch-only.

## Themen am Terminal

Terminal-Themen-Labels kommen aus den MFA-Einstellungen (Deutsch). Bei en/tr/ru/uk nutzt das Terminal optional die Browser-Translator-API (`browser-translator.ts`) — kein eigener i18n-Key pro Thema. Komponente: `BrowserTranslatedText.svelte`.

## Review-Checkliste

- Neue Keys nur in `de-DE.ts`, wenn die Oberfläche Staff ist
- Patienten-Locales nur für `terminal` / `portal` (und minimale `ui`) erweitern
- Neue Sprache: `terminal-patient-locales.ts` + Locale-Datei + `PATIENT_LANGUAGE_META` + OpenAPI-Enum + ggf. Tastatur-Layout
- Kein `t()` für rein deutsche Ops-/IT-Texte — Konstante oder Inline-Deutsch
